# Google managed-grant migration foundation

Internal checkpoint for Google Task3/Task6. Append-only schema37 adds immutable per-record legacy Google grant receipts; migrations1–36 remain unchanged. This is not live Google permission delivery, OAuth UI, discovery, or a completed whole-backup migration.

`importLegacyGoogleGrant` is trusted stopped-source migration code, with no HTTP route or browser actor impersonation. A row must map to an already imported enabled Google connection, using its exact connection import key. Legacy object_key must equal SHA256(`:` + exact Google file ID), matching wiki/provider_grants.py's Google namespace. The receipt retains original recipient spelling, legacy user key (including null/deleted user), desired/applied roles, permission ID, pending/synced/failed/revoked state and attempted timestamp. Invalid references/roles/recipient/input descriptors refuse with static errors. Historical freeform error text is not accepted or forwarded; grant status is preserved, but a full backup runner must separately report malformed/unmapped rows before cutover rather than silently drop them.

Import is atomic and idempotent by canonical source fingerprint, independent of input property order. A changed source under the same key refuses with MIGRATION_MISMATCH. Accepted replay after disable/reopen acknowledges history without changing the connection or re-enabling source access. New receipt context is also checked in SQL; update/delete are blocked. No local users, ACL, epoch, source bytes or remote permissions change. Source backup reads/manifests/whole-run orchestration still belong to the migration roadmap; no real user database was migrated here.

Private `googleManagedRecipients` checks current enabled Google connection revision in a read transaction, then retrieves at most10001 rows by indexed exact Google file ID. Over10000 refuses before constructing a worker allowlist. It returns a frozen deduplicated lowercase list. Recognition includes historical pending/failed/revoked recipients, as legacy google_managed did; it does not claim that sharing succeeded or grant local rights. Google IDs are global: legacy managed() queried provider+object_key across mounts. Receipt provenance stays attached to its original mount, while recognition of the same source ID works from another current connection. This does not bypass the metadata gate's central ownership/current-root/permission-list checks.

`CredentialVault.googleRecipients` requires the canonical minted connection object and rechecks its trusted binding/outgoing actor and caller authority before and after the asynchronous boundary and DB read. Copied/mutated config objects cannot supply recipient authority. Closing/reconfiguring/trashing a resource fences the scope, using the same rules as borrowed OAuth. The new lookup is composed with GoogleMetadata in a real SQLite/vault test without network calls. It is not yet wired to a public/source resolver because streamed content/native export remain incomplete.
