# Google upload capability journal

Task4 prerequisite on basebe9cfe7. This stores private resumable-upload receipts; it does not enable source uploads, conditional writes or the Google public resolver.

Append-only schema39 adds one retained journal row per existing delivery attempt. The canonical connection ID/revision and source reference are immutable. SQL requires a Google writing attempt with matching current source baseline/generation on insert. Phases move forward from reserved through initiating, ready and dispatched, or to unknown. A capability can be attached once, only during initiating→ready; SQL refuses replacement, deletion and backward transitions. Historical SQL1–38 is unchanged.

`GoogleUploadJournal` verifies the actual current job/attempt lease, immutable attempt facts, local read/write rights and connection/binding scope before reservation, state transitions or decryption. Caller copies cannot change document, revision, author, source digest/size, baseline or connection revision. Session URLs use the same strict capability validation as the status protocol, before encryption. The retained Fernet envelope includes a canonical identity tuple with the exact attempt/document/revision/author/digest/size/baseline/base revision/generation/connection/revision/reference. A valid ciphertext from another context is refused even if SQL protection was deliberately removed in the owned corruption fixture. Wrong encryption keys produce a static configuration error, without a URL in the error.

`CredentialVault.googleUploads` is available only on the exact outgoing connection minted by this vault. Binding/read-side scopes and copied connection objects cannot acquire it. Its private snapshot pins the attempt and job fields before caller mutation; returned methods cannot select another attempt. Ordinary methods check current scope and vault lifetime. Recording unknown is the deliberate exception: the current owned attempt may record uncertainty after revocation without decrypting or granting provider IO. Closing the vault fences this operation too.

Crash semantics: an expired writing owner is reclaimed by existing DeliveryAttempts as unknown. Loading a session is a receipt read, not permission to send. Initiating/dispatched cannot be restarted, reattached or reversed by the new owner. Lost initiation without a URL remains unknown rather than creating another session automatically. Retained capabilities have no deletion or retry shortcut; eventual session status/quiescence and verified readback must resolve the enclosing attempt.

Focused evidence:11 journal cases cover encryption/reopen, idempotent reservation, reclaimed owner/old lease, lost initiation, revoked users/configurations, canonical input, wrong provider, independent SQL guards, invalid URL/wrong key, encrypted context substitution, outgoing-only vault capability and two actual SIGKILL boundaries. The helper commits either initiating or dispatched, reports only that boundary and is killed. A new DB/lease owner observes the retained phase/URL, records unknown, cannot replay and does not advance provider_revision. These are real local journal-process crashes, not actual Google HTTP upload crashes.

Eight populated database upgrades31–38 preserve source versions, origins, inbox snapshots/quota/actions, OAuth refresh unknown receipts and imported Google grants across two opens; the new journal starts empty, foreign keys remain enforced and previous migration checksums remain unchanged. The previous15 upload-status cases continue to check the actual owned empty-PUT protocol.

Ruling: bind ciphertext to canonical immutable attempt/source context in addition to SQL constraints — Fernet alone authenticates bytes but not which row owns them — cost a small encrypted context tuple and current-scope checks on load. Ruling: persist uncertainty after revocation without decryption — denying a receipt write must not erase evidence of a possible remote dispatch — cost a narrowly owned metadata-only method. Ruling: no phase transition back to a sendable state after uncertainty — a local restart cannot establish that Google has stopped processing the prior request — cost explicit status/quiescence/readback work before enabling automatic delivery.
