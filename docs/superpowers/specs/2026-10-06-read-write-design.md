# Переход Yourwiki на read/write

Статус: согласовано пользователем; реализовано и проверено локально. 7 октября пользователь выбрал provider grants из task2.md вместо прежнего ограничения «только аккаунт подключения».

## Задача

По запросу пользователя заменить независимые visible/read/write на read/write, где write всегда включает read. Без read существование объекта не раскрывается. Упростить создание файлов, перенести управление доступом в настройки файла/папки, обеспечить единые проверки на всех поддерживаемых хранилищах.

Новые требования заменяют прежнее требование сохранять три независимых флага. Остальные требования task.md сохраняются: рекурсивное наследование, приоритет собственных ACL, отсутствие публичного sharing у провайдера, сохранность существующих файлов, совместное редактирование и контроль конфликтов.

## Что выявлено при ревизии

- AccessPolicy.allows в wiki/models.py проверяет независимые флаги. write не включает read.
- visible_docs, список папки и другие выборки фильтруют по visible. Поэтому имя доступно без возможности прочитать содержимое.
- require отдельно требует visible. Визуальные редакторы дополнительно проверяют read.
- Настройки ACL представлены отдельными policy-страницами; file_settings и folder_settings управляют историей.
- При создании администратору показывается полная матрица базовых и групповых ACL.
- Web-редактор ACL доступен администратору; API разрешает часть изменений владельцу. Такое расхождение нужно устранить.
- API создания документа не принимает расположение; API папок предоставляет только список. Это мешает единообразной работе с дополнительными mountpoint.
- Поддерживаются local, google, onedrive, github, sftp, smb. WebDAV упомянут в task.md как пример, но адаптера нет.
- Отказы сейчас намеренно возвращают общий HTTP 500. Отличие от 404 для отсутствующего объекта может раскрыть его существование по известному ID.

## Предлагаемая модель

1. В хранимой политике только булевы read/write. Запись нормализуется сервером: write=true устанавливает read=true. Отдельного visible нет в интерфейсе и новом API.
2. Без read объект отсутствует в списках, поиске, избранном, навигации, выборе расположения и ответах API. Запрос конкретного недоступного объекта возвращает такой же ответ, как запрос отсутствующего объекта. Доступный только для чтения объект при записи возвращает отказ без изменения файла.
3. Администратор сохраняет доступ. Неактивный/анонимный пользователь доступа не получает.
4. Сохраняются категории owner/group/everyone и дополнительные группы. Совпавшие явные групповые правила имеют приоритет над категориями; для нескольких совпавших групп разрешения объединяются. Новые персональные ACL вне владельца не добавляются без отдельного требования.
5. Файлы и подпапки наследуют ближайшую собственную политику предка. Изменение родителя сразу отражается в наследующих потомках. Собственные правила не изменяются. Доступ к отдельно открытому вложенному файлу не раскрывает недоступных родителей.
6. На корне используются настройки доступа пространства; исходная группа остаётся частью объекта. Перемещение меняет наследуемые права по новому родителю, собственные сохраняются.

## Создание и настройки

При создании — тип, название, расположение и содержимое/загрузка. Права автоматически наследуются; вместо матрицы — краткая подпись об этом. Основная группа выбирается автоматически по папке, а на корне — по доступной группе пользователя. Её можно изменить в настройках доступа, а не в основной форме создания.

Одна страница настроек файла/папки содержит раздел «Доступ» и отдельный раздел истории. В доступе: «Наследовать» / «Собственные права», получатели и два флага «Чтение» / «Запись». Включение записи включает чтение; отключение чтения снимает запись. Сервер обеспечивает это независимо от JavaScript. Показывается, откуда унаследованы права, без раскрытия закрытых имён.

Рекомендуемая граница изменения ACL — администратор, одинаково в UI и API. Само write не даёт права расширять ACL. Обычный редактор сохраняет доступ к остальным разрешённым настройкам. Старые ссылки на права ведут в раздел доступа настроек; дублирующие кнопки убираются.

## Переход со старых ACL

Миграция затрагивает политики файлов, папок, дополнительных групп и настройки пространства; не переписывает содержимое файлов или sharing провайдеров. Создаётся отчёт по неоднозначным старым правилам.

Предлагаемое безопасное правило: старый visible=false переносится в отсутствие доступа; при visible=true новый read = старый read OR старый write, новый write = старый write. Старое правило «виден, но читать нельзя» без write превращается в отсутствие доступа. Так скрытые ранее файлы не открываются автоматически, а действующая запись включает чтение.

Альтернатива, требующая явного выбора: полностью игнорировать прежний visible и переносить read OR write. Это сделает доступными ранее скрытые объекты с установленными read/write.

Миграция проверяется на фактических данных и на нескольких уровнях наследования. Откат не должен пытаться восстановить потерянный visible из нового read; исходные ACL сохраняются резервной копией перед рабочим обновлением.

## API и провайдеры

Рекомендуемый объём: единые проверки Yourwiki над всеми шестью существующими адаптерами. Каждый endpoint чтения/записи проходит общую проверку до обращения к адаптеру. Проверяются экспорт, импорт/создание в папке или mountpoint, обновление, PDF, вложения, история, оригинал, перемещение, удаление, source-session и WebSocket.

API создания получает папку/путь и проверяет write целевой папки. API доступа принимает нормализованные RW-политики, наследование и групповые правила. Изменение ACL не смешивается с изменением содержимого. Ошибки провайдера не расширяют разрешения Yourwiki и не приводят к успешному ответу на несостоявшуюся запись.

Уточнение получено: применить task2.md, добавить персональные ProviderGrant и отзыв. Google Drive и OneDrive получают пользовательские разрешения на отдельные файлы; папки не расшариваются, чтобы исключения дочерних ACL не обходились через внешнее наследование. GitHub выдаёт доступ ко всему репозиторию: уровень объединяется по всем доступным документам и mountpoint одного репозитория. Local/SMB/SFTP используют только локальные ACL.

ProviderIdentity связывает существующего участника Yourwiki с проверенным OAuth-профилем; один внешний аккаунт нельзя привязать к двум участникам. Завершение привязки требует имени профиля. Регистрация по приглашению остаётся основным способом вступления в закрытое пространство. Администратор настраивает OAuth clients; секреты зашифрованы, access tokens используются только для проверки профиля и не сохраняются.

ProviderGrant хранит получателя, объект, требуемую/применённую роль, receipt внешнего разрешения, состояние, ошибку и время попытки. Согласование запускается после commit ACL/членства/активности/identity; ошибки не откатывают локальные ACL. Отзыв выполняется до новой выдачи. Ошибки повторяются из UI или командой sync_provider_grants. Непривязанные аккаунты получают pending. Незавершённые приглашения GitHub остаются pending. Чужие публичные/неуправляемые разрешения блокируют обычные операции; публичные ссылки не создаются.

Ограничения: личный приватный GitHub-репозиторий не поддерживает read-only collaborator; ошибка показывается вместо повышения до write. Владелец внешнего хранилища сохраняет право собственности. Сбой отзыва может временно оставить внешний доступ; receipt сохраняется до успешного повтора. Изменения содержимого не запускают полную сверку grants. Команда повторной синхронизации проверяет также ранее успешные grants.

## Проверка результата

- Матрица read/write для владельца, основной группы, нескольких явных групп, остальных, администратора и неактивного пользователя.
- Миграция всех восьми комбинаций старых флагов; нормализация write-only запросов; строгая валидация ошибочного JSON.
- Наследование через несколько папок, собственные исключения, корень пространства, перемещение и смена членства в группах.
- Отсутствие утечки имени, ID, родительского пути, исходной ссылки и содержимого без read.
- Отзыв read/write при уже открытом редакторе/WebSocket, запрет записи через старую сессию.
- Прямые UI/API запросы с подменой ACL и расположения; отказ без вызова адаптера.
- Одинаковые контрактные проверки для шести провайдеров; реальные интеграционные проверки отдельно отмечаются как выполненные либо недоступные без учётной записи.
- Браузер: короткая форма создания, настройки файла/папки, взаимосвязь чекбоксов, сохранение и повторное открытие, телефон/компьютер.
- Обновление README, docs/task-acceptance.md и документации API; task.md остаётся исходным ТЗ с явным указанием заменённых требований в новой спецификации.
