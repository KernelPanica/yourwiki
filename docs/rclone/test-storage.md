# Тестовое Google Drive через rclone

Статус на 7 ноября 2026: тест завершён, подключение отключено, mount/bridge остановлены и исключены из автозапуска. Тестовые папки YourWiki/Drive перемещены в корзину по запросу пользователя. Рабочий корень `/` — папка Yourwiki через production rclone. Описание ниже относится к проведённому тесту.

Развёрнуто 7 ноября 2026 на сервере YourWiki. Отдельный тестовый источник, существующие документы и подключения не мигрировались.

Папка в приложении: https://yourwiki.kernelpanica.tech/folders/e2c4519b-3811-44db-8cee-c3ea6348c46d

Хранилище в настройках: **Google Drive через rclone (тест)**, тип «Папка сервера», ID `rclone-test`. Remote: отдельная помеченная папка **YourWiki rclone TEST** вне рабочего корня Google-хранилища. Локальная точка: `/root/yourwiki/instance/rclone-test/drive`.

## Что работает

- Постоянный rclone/FUSE mount с дисковым VFS-кешем, стартующий автоматически через systemd.
- Используется уже сохранённая авторизация центрального Google-подключения. Supervisor наблюдает изменение OAuth-контекста и перемонтирует тестовую папку. Это не монтирование личного диска каждого зарегистрированного пользователя.
- Служба mount объявляет готовность после появления FUSE и успешного чтения каталога. Web/provider имеют `Wants`/`After` и отдельный `ExecStartPre`-gate; с сохранённой авторизацией обычная незамонтированная директория не считается готовым диском. Во время первого подключения без авторизации сайт может запуститься для её настройки.
- Runtime-обрыв тестового mount не останавливает уже работающий сайт через `Requires`: операции именно с тестовым источником отказывают, рабочие источники продолжают использовать прежнее подключение.
- Создание папок/новых документов внутри тестовой папки доставляется через отдельный test bridge с локальным журналом. Дальнейшие изменения документа идут через существующий local provider, использующий смонтированные пути. База, CAS, журнал и кеш остаются на локальном диске.
- Источник можно просматривать/импортировать через существующие настройки хранилищ.
- Обязательный mount проверяется при открытии и дальнейших операциях. Закрепляется идентификатор FUSE mount, поэтому старый адаптер не продолжает работать после подмены mount.
- У FUSE служебные inode/ctime нестабильны при фоновой загрузке. Только для `requireMount:true` применён content fingerprint с повторной проверкой байтов именованного файла. Обычный локальный адаптер сохраняет прежние проверки stat identity. Устаревшее содержимое вызывает конфликт.

## Границы теста

Это не полная замена интеграции Google Drive. Сохранение в VFS означает фиксацию в локальном дисковом кеше, а не отдельное подтверждение Google в интерфейсе. Запись в Google проверена acceptance-тестом независимо по checksum. Оптимистическая проверка видит актуальное состояние mount; внешняя запись в Google до обновления его кеша ещё не является видимой. Для production-паритета нужны cloud preconditions/конфликтная логика.

Переносы/переименования ранее привязанных объектов, зеркалирование корзины и индивидуальных прав на стороне Drive не реализованы данным bridge. Google-native Docs/Sheets/Slides, длительный offline, массовая нагрузка и полный reboot сервера в этой проверке не испытывались. Изменение через rclone rename может менять исходный Drive ID — ID файлов не является частью local-provider reference. Пользоваться именно отдельной тестовой папкой.

## Проверено

- Unit tests: mount parser, точное совпадение FUSE пути/escaped paths, отказ для обычного каталога, сохранение работы обычного local provider.
- Существующие local adapter/storage route/crash tests прошли.
- Live `provision-main verify`: read/replace через mount, независимая checksum в Google, отказ устаревшей записи, импорт тестового Markdown в приложение.
- Live `rclone-test-acceptance.ts`: DocumentService.create → вложенная папка/файл в mount → source binding → DocumentService.save → provider_revision=2 → checksum реального Drive файла совпала.
- Перезапуск mount-службы с сохранённой авторизацией; зависимый bridge перезапускается через `PartOf`. После этого web/provider перезапущены и подтверждено, что timestamp готовности mount раньше их запуска.
- Негативный startup gate с теми же settings, но обычным временным каталогом: отказ, не «успешное» пустое хранилище.
- Все пять служб активны, HTTPS `/ready/` возвращает ready. Полный reboot не проводился.
- Общий typecheck имеет прежние ошибки в `provider-google-access-stage.test.ts`; проверка остальных исходников/тестов с исключением этого файла прошла.
- Браузерная вкладка открыла сайт, но была без сессии и показала логин. Авторизованная визуальная проверка папки в этом прогоне не заявляется.

## Эксплуатация

Службы: `yourwiki-rclone-test`, `yourwiki-rclone-test-bridge`. Templates: `deploy/rclone-test/`.

Секреты читаются из зашифрованного Google-подключения и передаются rclone через файл `0600` в `/run/yourwiki-rclone-test`, не через argv/логи. Кеш `/root/yourwiki/instance/rclone-test/cache` сохраняется между запусками. В тестовом supervisor rclone самостоятельно обновляет свой access token; повторная центральная авторизация обнаруживается и обновляет mount. Отдельная синхронизация редкой ротации refresh token из runtime rclone обратно в центральную БД не реализована.

Код: `apps/server/src/rclone/`. Проверка: `YOURWIKI_RCLONE_ACCEPTANCE=yes node apps/server/test/live/rclone-test-acceptance.ts WORKSPACE SETTINGS_JSON`. Она создаёт только свои тестовые объекты внутри явно provisioned тестовой папки.

При первоначальной настройке `Requires`-зависимость ошибочно остановила web/provider из-за сбоя mount. Зависимость была снята, сайт восстановлен; после исправления установлены `Wants`/`After` с проверкой перед стартом, без остановки уже работающего сайта при сбое mount. Ошибки root cause: rclone интерпретирует JSON token с пустым access_token как старый формат и теряет snake_case refresh_token; теперь используется непустой заведомо истёкший маркер и refresh. Rclone-процесс также не наследует NOTIFY_SOCKET — готовностью unit управляет supervisor.
