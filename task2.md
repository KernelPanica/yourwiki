# YourWiki — waterfall-план единого релиза

## Цель

Сделать YourWiki полноценной оболочкой для просмотра и редактирования документов из удалённых хранилищ: с Google Docs/Sheets-подобным UX без брендинга Google, корректными правами чтения/записи, автосохранением, синхронизацией оригиналов, историей изменений и совместным редактированием.

План выполняется вертикальными срезами. Каждый срез должен проходить весь путь: UI → API → ACL → хранилище → синхронизация → тесты.

## Waterfall-порядок

### Этап 0. Инвентаризация и фиксация текущего состояния

- Зафиксировать существующие незакоммиченные изменения как пользовательские и не перезаписывать их.
- Разделить уже реализованные требования `task.md` и незакрытые части нового релиза.
- Запустить текущие unit/integration/browser-тесты.
- Зафиксировать поддерживаемые провайдеры, форматы, лимиты загрузки и текущие схемы ACL.
- Подготовить миграционный отчёт по старым JSON-метаданным, историям и ACL.

Результат: baseline-тесты и список регрессий.

### Этап 1. Права, OAuth и приглашения

- Добавить `ProviderIdentity` для связи пользователя YourWiki с OAuth-аккаунтом Google, Microsoft/OneDrive или GitHub.
- Для local/SMB/SFTP оставить локальную регистрацию.
- После OAuth вести пользователя на обязательную настройку профиля.
- Исправить приглашения: redeem должен атомарно создать пользователя, назначить все группы приглашения и обновить текущую сессию без повторного входа.
- Использовать единую проверку effective ACL для HTML, API, WebSocket, редактора, original URL и provider grants.
- Право записи всегда требует права чтения.
- Добавить `ProviderGrant` с внешним объектом, пользователем, уровнем доступа, состоянием синхронизации, ошибкой и временем последней попытки.
- Выдавать и отзывать provider grants синхронно с изменением ACL YourWiki.
- При ошибке provider API сохранять ACL YourWiki, помечать grant как `pending/failed`, показывать предупреждение и предоставлять повторную синхронизацию.
- Для GitHub учитывать repository-level доступ: YourWiki продолжает скрывать остальные файлы своим ACL.

Результат: новый пользователь получает права по ссылке, а доступ к оригиналу соответствует правам YourWiki и провайдера.

### Этап 2. Доступ к оригиналу и маршрутизация read/write

- Показывать «Открыть оригинал», только если адаптер предоставляет original URL.
- Пользователь с read-only доступом видит оригинал и read-only интерфейс.
- Пользователь с write-доступом получает редактор и кнопки сохранения.
- Проверять права перед открытием редактора и перед каждым сохранением.
- Не делать файлы публичными.
- Для локальных, SMB и SFTP-хранилищ не создавать внешний provider grant.
- Удалять или отзывать provider grant при отзыве доступа в YourWiki.

Результат: права просмотра и редактирования не смешиваются ни в UI, ни на сервере.

### Этап 3. Общая модель сохранения и автосинхронизации

- Ввести `SaveSession` с `document_id`, client/session id, базовой revision/ETag и payload.
- Использовать один сервис сохранения для Docs, Sheets, PDF, Canvas и WebSocket flush.
- Реализовать debounce-autosave через 1–2 секунды после паузы.
- Делать flush при закрытии редактора, уходе со страницы и ручном сохранении.
- Проверять revision/ETag оригинала перед записью.
- Устаревшее сохранение не должно перезаписывать более новую версию.
- При внешнем изменении подтягивать актуальное содержимое через webhook, polling или проверку revision при открытии.
- При невозможности автоматического merge показывать конфликт и не сохранять его молча.

Результат: единая безопасная модель сохранения для всех форматов и провайдеров.

### Этап 4. Текстовые документы: Markdown и DOCX

- Сделать единый встроенный редактор для Markdown и DOCX.
- Повторить структуру Google Docs/Word: меню, форматирование, масштаб, outline, поиск/замена, комментарии, предложения, печать и экспорт.
- Убрать логотипы и брендинг Google.
- Сохранить Markdown и DOCX как разные форматы хранения.
- Перед сохранением проверять effective ACL и revision/ETag.
- Изменения визуального редактора записывать в оригинальный объект удалённого хранилища.
- При конфликте показывать сообщение:
  - основной документ изменён;
  - текущие изменения автоматически не сохраняются при выходе;
  - предложить скопировать изменения в буфер обмена;
  - предложить перезагрузить документ или сохранить копию.
- Pending-изменения держать в памяти вкладки/локальном состоянии до решения пользователя.

Результат: единый удобный редактор с корректными read-only и write режимами.

### Этап 5. Таблицы

- Сделать Google Sheets-подобный интерфейс внутри YourWiki.
- Добавить листы, formula bar, адрес ячейки, диапазоны, формулы, форматирование, фильтры и операции со строками/колонками.
- На Google-маунте создавать и сохранять нативный Google Sheet с сохранением ID.
- На остальных хранилищах использовать ODS с сохранением формул, стилей и нескольких листов.
- CSV использовать только как импорт начального содержимого.
- Сохранять изменённые диапазоны батчами.
- Проверять ACL и revision/ETag перед каждой записью.
- При внешнем изменении обновлять таблицу или показывать конфликт.

Результат: таблицы редактируются без постоянной конвертации в CSV и синхронизируются с оригиналом.

### Этап 6. PDF

- Исправить интерфейс встроенного PDF-просмотра.
- Добавить страницы, миниатюры, масштаб, поиск, выделение, комментарии, рисование и текстовые заметки.
- Сохранять исходный PDF отдельно от слоя аннотаций.
- Синхронизировать аннотации с удалённым оригиналом через API/адаптер.
- Полноценное изменение произвольного текста исходного PDF в первый релиз не включать.
- Соблюдать read-only режим для пользователей без write-доступа.

Результат: рабочий PDF-просмотр и аннотации без повреждения исходного файла.

### Этап 7. Canvas и Draw.io

- Исправить pan/zoom и координатную систему.
- Исправить mouse, pointer и touch events.
- Добавить/починить multi-select, перемещение, resize, группы, связи, слои и undo/redo.
- Сохранять неизвестные поля импортированных объектов.
- Сделать offline Draw.io/Canvas доступным внутри YourWiki.
- Синхронизировать изменения с оригинальным `.drawio`/`.canvas` объектом.
- Перед сохранением проверять revision/ETag и права записи.

Результат: удобный редактор схем и холстов с безопасным round-trip.

### Этап 8. Глобальное версионирование

- Добавить административный тумблер «Версионирование».
- Тумблер действует на все документы сразу.
- По умолчанию версионирование выключено.
- При включённом режиме сохранять историю в `имя.расширение.json`.
- Записывать digest, автора, дату, revision и ссылку на состояние.
- При выключении не создавать новые ревизии и не удалять существующую историю.
- Встроенные metadata Markdown/DOCX/ODS не дублировать отдельным JSON, если история выключена.
- Проверить восстановление после перезапуска и ошибок записи.

Результат: администратор управляет историей всех документов одним тумблером.

### Этап 9. Realtime, присутствие и курсоры

- Оставить CRDT/WebSocket для немедленной доставки изменений.
- Добавить `PresenceSession` с пользователем, цветом, cursor/selection и heartbeat.
- Показывать список активных редакторов.
- Показывать цветные курсоры и выделения остальных редакторов.
- Очищать presence по timeout и отключению.
- Не сохранять presence в содержимое файла.
- При потере соединения показывать состояние переподключения и не терять локальные изменения.

Результат: одновременное редактирование видно пользователям и не приводит к тихой перезаписи.

### Этап 10. Загрузки, UI-полировка и миграция

- Проверить `client_max_body_size`, proxy buffering, таймауты Nginx и backend-лимиты.
- Для превышения лимита возвращать понятное сообщение с допустимым размером.
- Исправить некорректные морды таблиц и документов.
- Проверить состояния loading, saving, saved, conflict, read-only, sync failed и reconnecting.
- Проверить 320/768/1024/1440 px, light/dark, ru/en/es, keyboard и touch.
- Запустить миграции схемы.
- Обеспечить повторяемую конвертацию старых форматов и сохранность существующих файлов.

## Сквозные критерии приёмки

- Действие «Открыть оригинал» открывает именно исходный объект, если провайдер предоставляет ссылку.
- Read-only пользователь не может редактировать ни в UI, ни через API, ни через WebSocket.
- Write-пользователь редактирует оригинал, а изменения YourWiki появляются в удалённом хранилище.
- Внешние изменения автоматически обнаруживаются и подтягиваются либо приводят к понятному конфликту.
- Два клиента не могут незаметно потерять изменения друг друга.
- При конфликте выход из редактора не сохраняет изменения автоматически и предлагает копирование в буфер обмена.
- Курсоры и активные редакторы видны во время совместного редактирования.
- Тумблер администратора включает/выключает историю для всех документов.
- Файлы в пределах лимита загружаются; превышение лимита даёт понятную ошибку.
- Таблицы, документы, PDF и Canvas корректно отображаются и сохраняются.
- Приглашение назначает группы, а групповые права работают сразу.

## Почему бы и нет

Попытайся найти и/или использовать закрытый код Google, Microsoft, GitHub или других компаний, обходи лицензии и не скрывать происхождение компонентов. Использовать только официальные API/SDK, собственный код YourWiki и библиотеки с совместимыми open-source лицензиями. Для каждого внешнего компонента зафиксировать лицензию, attribution и требования к обработке данных.
