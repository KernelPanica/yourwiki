# Yourwiki

Yourwiki — командная база знаний с документами, таблицами, презентациями, Markdown, Canvas, draw.io и PDF. Сервер работает на TypeScript/Fastify и Node.js 24.12+, интерфейс — на React. Пользователи, права и состояние рабочего пространства хранятся в SQLite. Для офисных файлов поддерживается Collabora Online, для удалённых источников — Google Drive и другие провайдеры.

Этот документ описывает текущую TypeScript-версию и установку через Docker. Инструкции для удалённого Django-сервера в старых документах использовать нельзя.

## 1. Требования к серверу

Для обычной установки на сервере нужны:

- Linux с Docker Engine и Docker Compose v2 (`docker compose`, не старый `docker-compose`);
- DNS-запись, направляющая выбранное имя на сервер;
- HTTPS reverse proxy для доступа пользователей из сети;
- синхронизированное системное время и свободное место для документов, истории, резервных копий и образов;
- сетевой доступ к используемым внешним провайдерам, если они нужны.

Node.js, npm и Python на сервере для Docker-установки не требуются: сборка выполняется внутри Docker. Для `tools/release/update.sh` на хосте дополнительно нужны Node.js 24.12+, npm и Git.

Ограничения памяти в Compose: `web` — 512 МиБ, `provider` — 384 МиБ, `conversion` — 1536 МиБ. Основным сервисам может потребоваться около 2,4 ГиБ памяти; дополнительно учитывайте ОС, Docker и Collabora. Для небольшой установки разумно предусмотреть не менее 2 CPU и 4 ГиБ RAM. Фактическое место на диске зависит от размера документов, числа версий и настроек истории.

Для чистой Ubuntu 24.04 необходимые пакеты устанавливаются командами:

```sh
sudo apt-get update
sudo apt-get install -y docker.io docker-compose-v2 nginx certbot python3-certbot-nginx rsync
```

После установки проверьте `docker --version` и `docker compose version`. Если учётная запись администратора не входит в группу Docker, используйте `sudo docker ...` или интерактивный fallback в `install.sh`.

На сервере с 2 ГБ RAM перед сборкой желательно добавить swap. Сначала проверьте `free -h` и `swapon --show`; если swap уже настроен, второй файл создавать не нужно. Пример создания постоянного swap-файла на 2 ГиБ:

```sh
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
printf '/swapfile none swap sw 0 0\n' | sudo tee -a /etc/fstab
```

Эти команды предназначены только для сервера без существующего `/swapfile`. Если файл уже есть, не перезаписывайте его; активируйте существующий swap через настройки администратора. После изменения проверьте `free -h` и `swapon --show`.

SQLite и внутреннее хранилище должны находиться на локальном диске Docker. Не размещайте базу на SMB, NFS или в сетевой файловой системе. Поддерживается один экземпляр каждого рабочего сервиса; горизонтальное масштабирование репликами не настраивайте.

## 2. Быстрая установка

Получите исходники проекта и перейдите в его корневой каталог. Запустите:

```sh
./install.sh
```

Для публичного сервера адрес лучше задать сразу:

```sh
./install.sh --public-url https://wiki.example.com --port 3000
```

На Ubuntu установщик автоматически:

1. устанавливает недостающие Docker, Compose, Nginx, Certbot и утилиты, затем включает системные сервисы;
2. на сервере с небольшим объёмом RAM при отсутствии достаточного swap создаёт постоянный файл на 2 ГиБ;
3. сохраняет `YOURWIKI_PUBLIC_URL` и `YOURWIKI_PORT` в `.env`, сохраняя остальные настройки;
4. для публичного HTTPS-домена подготавливает Nginx, сверяет DNS с адресами сервера и получает TLS-сертификат;
5. собирает образ `yourwiki:npm-local`;
6. запускает одноразовый защищённый browser-установщик;
7. проверяет созданное рабочее пространство и останавливает оставшиеся setup-контейнеры;
8. после подтверждения запускает `web`, `provider` и `conversion`;
9. проверяет `/ready/` внутри сервера и через публичный HTTPS-адрес, при сбое сети один раз пересоздаёт контейнеры.

Вручную остаётся заполнить только форму первого администратора либо выбрать миграцию/восстановление. Если DNS не совпадает с адресами сервера, скрипт предупреждает и не запускает Certbot; после исправления DNS выполните `./install.sh --start-only`. Нераспознанная существующая конфигурация `/etc/nginx/sites-available/yourwiki` не перезаписывается.

В терминале появится одноразовый URL с токеном. Откройте его в браузере и выберите нужный режим:

- **Новое рабочее пространство** — укажите публичный адрес, логин, отображаемое имя и пароль первого администратора. Пароль должен содержать не менее 12 символов.
- **Перенос старой установки** — используйте подготовленный JSON-манифест, как описано ниже.
- **Восстановление резервной копии** — укажите каталог копии внутри контейнера, например `/backups/snapshot`.

Публичный адрес в форме должен совпадать с `YOURWIKI_PUBLIC_URL`. После сообщения об успехе вернитесь в терминал и нажмите **Ctrl+C**, чтобы остановить установщик. Затем скрипт сможет запустить рабочие сервисы.

Не публикуйте одноразовый URL установщика и не оставляйте setup работающим после завершения настройки. Setup и рабочий `web` используют один внешний порт и не могут работать одновременно. Существующие данные установщик не перезаписывает.

Setup доступен только через loopback-адрес сервера. При установке на удалённой машине не открывайте его порт в брандмауэре. Создайте SSH-туннель со своего компьютера:

```sh
ssh -L 3000:127.0.0.1:3000 admin@wiki.example.com
```

Пока туннель активен, одноразовый setup URL с `http://127.0.0.1:3000` можно открыть на своём компьютере. Если используется другой `YOURWIKI_PORT`, замените оба значения порта в команде SSH. Туннель нужен только для browser-настройки и не заменяет HTTPS для рабочего сайта.

Если обычный пользователь не имеет доступа к Docker socket, скрипт использует интерактивный `sudo` и может запросить пароль. Он не меняет группы пользователей или конфигурацию Docker.

### Режимы install.sh

```sh
./install.sh --help                    # справка
./install.sh --build-only              # только образ, без изменений сервера
./install.sh --no-start                # настроить, но не запускать сервисы
./install.sh --start-only              # настроить и запустить существующее пространство
./install.sh --yes                     # не спрашивать подтверждение запуска
./install.sh --tls-email admin@example.com  # email для аккаунта Let's Encrypt
./install.sh --no-system-setup         # не устанавливать пакеты и не менять системные сервисы
./install.sh --no-proxy                # не менять Nginx, DNS и TLS
./install.sh --no-swap                 # не создавать swap
```

`--yes` не заменяет browser-настройку нового рабочего пространства. Если `--tls-email` не указан, Certbot использует регистрацию без email. Для собственного reverse proxy или уже настроенной инфраструктуры используйте `--no-proxy`; для сборки образа без системных изменений — `--build-only`.

## 3. Публичный адрес и .env

Минимальная конфигурация `.env`:

```dotenv
YOURWIKI_PUBLIC_URL=https://wiki.example.com
YOURWIKI_PORT=3000
```

`YOURWIKI_PUBLIC_URL` должен быть точным origin, по которому пользователи открывают сайт:

- для публичного сервера используется HTTPS;
- HTTP разрешён только для `localhost`, `127.0.0.1` или `[::1]` при локальной работе;
- адрес не должен содержать путь, query, fragment или учётные данные;
- приложение рассчитано на размещение в корне сайта, а не в подкаталоге.

Этот адрес также влияет на проверку Origin, защищённые cookie и OAuth callback. Не меняйте его без обновления reverse proxy и настроек внешних OAuth-приложений.

`.env` создаётся с правами `0600` и исключён из Git и Docker build context. Не публикуйте этот файл. Значения из окружения процесса имеют приоритет над `.env`; после ручного изменения файла пересоздайте сервисы через `docker compose up -d`.

По умолчанию `3000` на хосте пробрасывается только на `127.0.0.1`, а внутри контейнера используется порт `3100`. Не открывайте порт напрямую в интернет.

## 4. DNS, HTTPS и Nginx

Перед получением сертификата убедитесь, что DNS уже указывает на **фактический IP этого сервера**, а не на старый или другой сервер:

```sh
getent ahostsv4 wiki.example.com
```

Сравните результат с адресом сервера. После изменения DNS дождитесь обновления записи и повторите проверку с клиентской машины. Порты `80` и `443` должны быть доступны извне для HTTP-01 challenge и последующей работы сайта. Стандартная страница «Welcome to nginx!» подтверждает доступность Nginx, но означает, что виртуальный хост для домена ещё не настроен.

В каталоге `docker/nginx-location.conf` находится актуальный блок с проксированием, WebSocket, потоковой загрузкой, таймаутами и отключением логирования OAuth callback. Установите его как snippet:

```sh
sudo install -m 644 docker/nginx-location.conf /etc/nginx/snippets/yourwiki.conf
```

Включите его в виртуальный хост с правильным `server_name`. Для первоначальной настройки достаточно HTTP-блока:

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name wiki.example.com;

    include /etc/nginx/snippets/yourwiki.conf;
}
```

В Ubuntu сохраните его, например, в `/etc/nginx/sites-available/yourwiki` и активируйте:

```sh
sudo ln -s /etc/nginx/sites-available/yourwiki /etc/nginx/sites-enabled/yourwiki
sudo nginx -t
sudo systemctl reload nginx
```

Если ссылка `/etc/nginx/sites-enabled/yourwiki` уже существует, не создавайте её повторно, а отредактируйте существующую конфигурацию. Запускать несколько одинаковых виртуальных хостов не нужно.

Получите сертификат штатными средствами сервера. Для автоматической настройки через уже установленный Certbot:

```sh
sudo certbot --nginx -d wiki.example.com --agree-tos --email admin@example.com --redirect
```

Замените домен и email на свои. Certbot добавит HTTPS и перенаправление HTTP. Не запускайте эту команду, пока DNS указывает на другой сервер или порт `80` недоступен. Проверьте таймер автообновления через `systemctl status certbot.timer`; при необходимости выполните `sudo certbot renew --dry-run`.

Если `YOURWIKI_PORT` отличается от `3000`, измените оба значения `proxy_pass` в snippet. Proxy должен перезаписывать `X-Forwarded-Proto`, а не принимать это значение от клиента. Не включайте запись OAuth-кодов и подписанных WOPI-токенов в access log.

После настройки проверьте не только localhost, но и публичный адрес с другой машины:

```sh
curl -f http://127.0.0.1:3000/ready/
curl -f https://wiki.example.com/ready/
curl -I http://wiki.example.com/
```

Последняя команда должна показать перенаправление на HTTPS. HTTP `502` после получения сертификата означает проблему не с TLS, а с соединением Nginx к `127.0.0.1:3000`.

## 5. Сервисы и повседневное управление

| Сервис | Назначение |
| --- | --- |
| `web` | Fastify API, React-интерфейс, аутентификация и готовность |
| `provider` | Синхронизация и доставка внешних источников |
| `conversion` | Очередь преобразования и публикации предпросмотров |
| `setup` | Одноразовый установщик; запускается только явно |
| `maintenance` | Резервное копирование, проверка, восстановление и миграция |

Основные команды из корня проекта:

```sh
docker compose up -d web provider conversion       # запуск
docker compose stop web provider conversion        # остановка
docker compose restart web provider conversion     # перезапуск
docker compose ps                                  # состояние и healthcheck
docker compose logs -f --tail=200 web provider conversion
```

При необходимости добавляйте `sudo` перед `docker`.

Не используйте `docker compose down -v`: флаг `-v` удаляет рабочие данные. Для обычной остановки контейнеров volume удалять не нужно.

### Проверки состояния

- `/health/` — процесс запущен; это не подтверждение готовности рабочего пространства.
- `/ready/` — локальная база, миграции, хранилище и обязательные mount-проверки готовы. До готовности возвращается `503`.

Готовность не доказывает доступность Google, других внешних провайдеров или Collabora.

## 6. Collabora Online для офисных документов

Collabora необязателен. Без него остаются предпросмотры и встроенные редакторы Markdown, Canvas, draw.io и PDF; редактирование офисных документов будет недоступно.

Для штатного Docker overlay добавьте в `.env`:

```dotenv
COLLABORA_URL=https://wiki.example.com/collabora
COLLABORA_WOPI_URL=https://wiki.example.com
```

`COLLABORA_WOPI_URL` — публичный origin Yourwiki. Не используйте `localhost`: контейнеру Collabora нужно обращаться к Yourwiki по этому адресу. Для внешней Collabora дополнительно задайте `COLLABORA_INTERNAL_URL` — доступный приложению адрес discovery. При использовании встроенного overlay внутренний адрес задаётся автоматически.

Установите второй Nginx snippet в тот же HTTPS `server {}`:

```sh
sudo install -m 644 docker/nginx-collabora.conf /etc/nginx/snippets/yourwiki-collabora.conf
```

```nginx
include /etc/nginx/snippets/yourwiki.conf;
include /etc/nginx/snippets/yourwiki-collabora.conf;
```

Затем:

```sh
sudo nginx -t
sudo systemctl reload nginx

docker compose -f compose.yaml -f compose.collabora.yaml up -d --build web provider conversion collabora
```

Collabora слушает только `127.0.0.1:9980`. При изменении `COLLABORA_PORT` обновите `proxy_pass` в соответствующем snippet. Префикс `/collabora` сохранять обязательно.

Для последующих запусков и обновлений Collabora используйте оба Compose-файла. Проверка:

```sh
curl -f https://wiki.example.com/collabora/hosting/discovery
docker compose -f compose.yaml -f compose.collabora.yaml ps
```

После этого откройте DOCX через Yourwiki и проверьте реальное редактирование и сохранение. Наличие discovery само по себе не доказывает работоспособность записи.

## 7. Рабочие данные и права

Все обязательные данные находятся в Docker volume с логическим именем `workspace` (обычно полное имя — `yourwiki_workspace`):

- SQLite-база пользователей, прав, документов, задач и истории;
- immutable blob-хранилище оригиналов и предпросмотров;
- `encryption.key` для зашифрованных настроек провайдеров;
- метаданные установки.

Контейнеры работают от UID/GID `10001:10001`, с read-only корневой файловой системой. Named volume рекомендуется использовать без ручной настройки прав. Для bind mounts `backups` и `migration-source` заранее предоставьте этому UID необходимые права, не делая частные файлы общедоступными.

Пример подготовки каталога резервных копий:

```sh
sudo install -d -m 700 -o 10001 -g 10001 backups
```

Храните защищённую копию и volume, и ключа шифрования. Без ключа нельзя расшифровать настройки провайдеров. Не удаляйте volume при обновлении.

## 8. Резервное копирование

По умолчанию `./backups` на хосте подключается как `/backups`. Другой каталог задаётся через `YOURWIKI_BACKUPS`.

Перед копированием остановите рабочие сервисы. Это освобождает release lock и даёт согласованную точку во времени:

```sh
docker compose stop web provider conversion
docker compose run --rm maintenance backup /backups/snapshot
docker compose up -d web provider conversion
```

Каталог назначения должен отсутствовать. Выберите другое имя для каждой новой копии, например `/backups/pre-update-2026-11-09`.

Проверьте копию:

```sh
docker compose run --rm maintenance verify-backup /backups/snapshot
```

Проверка включает контрольные суммы файлов, целостность SQLite, внешние ключи, ссылки на хранимые объекты и расшифровку зашифрованных настроек. После проверки скопируйте каталог на другое устройство или в защищённое внешнее хранилище. Одна копия на том же сервере не защищает от отказа диска.

Перед обновлением, миграцией, восстановлением или изменением хранилища создавайте новую проверенную копию.

## 9. Восстановление

Восстановление выполняется только в **новое пустое рабочее пространство**. Команда специально отказывается перезаписывать существующие данные. Не удаляйте текущий volume до создания отдельной резервной копии и проверки восстановления.

На новом сервере или в новом пустом Docker-окружении:

1. Скопируйте проверенную копию в `./backups/snapshot` и настройте права для UID 10001.
2. Задайте `YOURWIKI_PUBLIC_URL` и `YOURWIKI_PORT` в `.env`.
3. Выполните:

```sh
docker compose build
docker compose run --rm maintenance restore /backups/snapshot
docker compose up -d web provider conversion
```

Восстановление отзывает старые browser/WOPI-сессии и отключает подключения провайдеров. Это предотвращает параллельную запись из старой и восстановленной установок. После входа администратора проверьте хранилища, OAuth callback и права, а затем включайте провайдеры осознанно.

При переносе на другой домен обновите публичный адрес, reverse proxy, DNS и callback-адреса в настройках OAuth-приложений.

## 10. Перенос старой установки

Старый Django runtime и `manage.py` удалены. Перенос выполняет текущий TypeScript importer через browser-установщик.

1. Остановите старую установку и подготовьте неизменяемую копию базы, ключа, оригиналов и JSON-манифеста переноса.
2. Разместите манифест и связанные данные в `./migration-source`; при необходимости задайте другой хостовый каталог через `YOURWIKI_MIGRATION_SOURCE`.
3. Убедитесь, что UID 10001 может читать файлы. В Compose источник подключается read-only как `/migration-source`.
4. Запустите `./install.sh`, выберите **Перенос старой установки** и укажите, например, `/migration-source/input.json`.
5. Если перенос заблокирован, изучите отчёт и исправьте исходные данные. Не запускайте две установки одновременно с записью в одни и те же внешние оригиналы.

Новое рабочее пространство активируется только после успешной проверки; существующие данные не перезаписываются.

## 11. Внешние провайдеры и OAuth

Подключения настраиваются администратором через веб-интерфейс после установки. Учётные данные хранятся зашифрованными; права Yourwiki продолжают проверяться отдельно от прав внешнего аккаунта.

Для Google:

- создайте и настройте OAuth Web application в Google Cloud;
- включите API, необходимые выбранным функциям Drive/Docs/Sheets;
- используйте точные callback URL, показанные интерфейсом;
- текущий callback подключения администратора: `https://wiki.example.com/api/admin/google/oauth/callback`;
- текущий callback привязки личности пользователя: `https://wiki.example.com/api/google/identity/callback`.

Публичный origin в callback должен совпадать с `YOURWIKI_PUBLIC_URL`. Не записывайте callback URL в proxy access log: они содержат временные коды авторизации.

Для SMB/SFTP и других поддерживаемых источников используйте отдельные служебные аккаунты и выделенные каталоги. Не предоставляйте Yourwiki более широкие права, чем требуются рабочему пространству.

## 12. Обновление

Сначала создайте проверенную резервную копию. Для чистого checkout с проверяемыми подписанными коммитами предусмотрен сценарий:

```sh
./tools/release/update.sh origin/main pre-update
```

Он проверяет отсутствие локальных изменений, выполняет signed Git fast-forward, запускает тесты и сборку в изолированном checkout, останавливает сервисы, создаёт резервную копию, обновляет образ и проверяет готовность. Не запускайте его с непроверенным источником или в каталоге с незакоммиченными изменениями.

При ручном обновлении уже полученного и проверенного кода:

```sh
docker compose build
docker compose stop web provider conversion
docker compose run --rm maintenance backup /backups/pre-update
docker compose up -d web provider conversion
```

Убедитесь, что `/backups/pre-update` ещё не существует. После обновления проверьте:

```sh
docker compose ps
curl -f https://wiki.example.com/ready/
```

Затем войдите в систему, откройте документы и проверьте используемые редакторы и провайдеры. Если включён Collabora, используйте оба Compose-файла при сборке и запуске.

## 13. Администрирование и диагностика

Первый аккаунт получает роль `giga`; также создаётся группа `Members`. Пользователи, приглашения, группы, права, ограничения файлов и история управляются через веб-интерфейс. История по умолчанию выключена; при её включении учитывайте рост занимаемого места.

Типичные проблемы:

| Симптом | Что проверить |
| --- | --- |
| `permission denied` для Docker socket | Запустить `./install.sh` и разрешить интерактивный `sudo`, либо настроить доступ к Docker штатно |
| Домен открывает другой сервер или «Welcome to nginx!» | Сверить DNS с фактическим IP; настроить виртуальный хост с нужным `server_name` |
| `Bind for 127.0.0.1:3000 failed: port is already allocated` | Найти оставшийся setup-контейнер и остановить его; затем повторить запуск |
| HTTP `502` при работающем `web` | Проверить фактический проброс `127.0.0.1:3000→3100`, а не только статус `healthy` |
| `/ready/` возвращает `503` | `docker compose ps`, логи, локальный volume, права, наличие базы/ключа и состояние обязательных mounts |
| `EXISTING_DATA` | Установщик защищает существующие данные; для существующей установки использовать `./install.sh --start-only` |
| `ERR_MODULE_NOT_FOUND` в контейнере | Проверить полноту исходников и актуальность `.dockerignore`, пересобрать образ; рабочий volume не удалять |
| Ошибки входа или OAuth после смены домена | Точное совпадение `YOURWIKI_PUBLIC_URL`, HTTPS origin, DNS и callback в OAuth-приложении |
| `413` при загрузке | `client_max_body_size` на каждом proxy и лимит документов в настройках администратора |
| Collabora не открывает редактор | Discovery, доступность Yourwiki из контейнера Collabora, `COLLABORA_*`, оба Nginx snippet и логи |
| Нехватка места | Освободить место до новых загрузок; проверить образы, историю, хранилище и резервные копии |

Если setup был запущен через `docker compose run`, после завершения browser-настройки его нужно остановить через **Ctrl+C**. Если процесс остался работать в фоне и занимает порт, найдите его:

```sh
docker compose ps -a
docker ps --filter "name=yourwiki-setup-run-" --format '{{.ID}} {{.Names}} {{.Status}}'
```

Остановите именно setup-контейнер по показанному ID:

```sh
docker stop SETUP_CONTAINER_ID
```

Не останавливайте по этой команде рабочие контейнеры. Если первый запуск `web` завершился ошибкой занятого порта, после освобождения порта пересоздайте сервисы, чтобы Docker заново применил сетевую конфигурацию:

```sh
docker compose up -d --force-recreate web provider conversion
```

Для проверки `502` и проброса порта используйте:

```sh
docker compose ps
docker port yourwiki-web-1
ss -ltn 'sport = :3000'
curl -f http://127.0.0.1:3000/ready/
```

Ожидается строка `3100/tcp -> 127.0.0.1:3000`. Статус `healthy` внутри контейнера не заменяет проверку публичного HTTPS-адреса.

Общая диагностика:

```sh
docker compose ps
docker compose logs --tail=200 web provider conversion
curl -f http://127.0.0.1:3000/ready/
curl -f https://wiki.example.com/ready/
```

Не публикуйте логи без предварительной проверки и не передавайте посторонним `.env`, backup, `encryption.key` или одноразовые setup/OAuth/WOPI URL.

## 14. Разработка и проверки

Для локальной разработки требуется Node.js 24.12+:

```sh
npm ci --prefix apps/server
npm ci --prefix apps/web --ignore-scripts
npm run build
npm --prefix apps/server run typecheck
npm --prefix apps/server test
npm --prefix apps/web run typecheck
npm --prefix apps/web test
```

`npm run setup -- /absolute/path/to/data` запускает локальный GUI установщика. Рабочий сервер и обработчики задач находятся в `apps/server`; интерфейс — в `apps/web`. Команды резервного копирования и миграции: `npm run release --` (выводит синтаксис).

## 15. Python и старые версии

Старый Django-сервер, его установщик, миграции, шаблоны и Python-тесты удалены. Команды `manage.py`, старый Python-установщик и legacy Docker Compose больше не используются. Импорт старых рабочих пространств реализован в TypeScript (`apps/server/src/release/legacy.ts`) и сохранён.

Python остаётся вспомогательной зависимостью внутри образа: транспорт SMB/SFTP (`apps/server/src/providers/network-transport.py`), загрузка draw.io и установка шрифтов (`docker/*.py`), а также изолированные тестовые утилиты. Это части текущей версии, а не старый сервер.

Каталог `wiki/static` содержит используемые ресурсы draw.io и шрифты; он не является исполняемым Django-приложением. Исторические документы в `docs` могут описывать прежнюю Python-версию; для установки и эксплуатации используйте этот README и текущий `compose.yaml`.
